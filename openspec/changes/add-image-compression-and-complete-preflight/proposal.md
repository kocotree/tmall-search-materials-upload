## Why

第三阶段的历史候选数据没有稳定携带原图文件大小、宽高和比例，页面因此显示“文件大小未知 / 比例未知”，也无法按平台的最小尺寸、文件大小及目标比例要求给出可靠提示。现有压缩能力只有接口契约，没有可用实现，导致大于 20MB 的图片虽然能被选择，却无法形成可进入第五阶段的合规输出。

## What Changes

- 第三阶段在候选生成时读取并持久化原图文件大小、EXIF 纠正后的宽高、原始比例、格式、SHA-256、可读性以及针对 1:1/3:4 的最大可裁剪尺寸。
- 第三阶段图片卡片固定展示原图尺寸、原始比例、原图文件大小、推荐分辨率比较和最终处理结论；读取失败时显示明确错误并禁止采用，不再用“未知”掩盖缺失预检。
- 将图片策略补全为统一的硬规则与建议规则：最小宽高 720×720、文件大小 200KB–20MB、允许输出比例 1:1/3:4、推荐尺寸 1440×1440 和 1440×1920。
- 增加任务本地的 Pillow 图片压缩提供方，支持“仅压缩”和“裁剪后压缩”，保留共享盘原图，只把派生文件写入时间戳任务目录。
- 第四阶段同时展示原图与处理后文件的大小、尺寸、比例、格式、质量、处理动作和来源链，并允许确认“直接使用 / 裁剪 / 压缩 / 裁剪并压缩 / 仅作候选 / 排除”。
- 第五阶段在接收坑位前重新校验当前 revision 的确认输出、200KB–20MB、最小宽高、1:1/3:4、每坑 3–9 张及坑位内比例一致性。
- 历史任务进入第三阶段时重新检查候选原文件并生成新版预检数据，不允许缺少关键原图信息的旧候选直接进入后续阶段。
- **BREAKING**：大于 20MB 的图片只有在当前任务存在可用压缩能力时才允许采用；小于 200KB、无法产生至少 720×720 合规输出或无法读取的图片禁止采用。

## Capabilities

### New Capabilities

- `image-preflight-and-compression`: 定义完整原图预检信息、第三阶段合规提示与可选性、任务本地图片压缩、第四阶段原图/输出审查，以及第五阶段最终输出强校验。

### Modified Capabilities

无。上一轮 `image-compliance-review` 仍是尚未归档的已完成变更，本提案以新的增量能力描述其后续行为，不改写已验收提案。

## Impact

- 影响第三阶段候选生成、候选 JSON Schema、图片卡片和历史任务重建逻辑。
- 影响任务级图片策略、图片合规分类器、第四阶段处理决定及派生文件生成。
- 影响第五阶段坑位输入校验、原因码和审计来源链。
- 新增 Pillow 压缩实现，但不增加外部可执行程序或网络服务依赖；AI 裁剪仍只保留接口，不在本变更内实现。
- 需要更新 `SKILL.md`、操作文档、`test_plan.md`，并补充边界值、格式兼容、源文件不变性、历史任务和浏览器交互测试。
