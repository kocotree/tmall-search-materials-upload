## Context

现有第三阶段部分候选只有路径和缩略图，没有完整 `size_bytes` 与图片预检数据，因此页面无法显示真实原图大小和比例。第四阶段已有人工裁剪、压缩接口契约及最终坑位校验框架，但没有实际压缩提供方；现行行为还允许所有大于 20MB 的图片先被采用，即使当前任务没有能力生成合规输出。

平台规则包含硬门槛和软建议：图片宽高至少 720×720、文件大小为 200KB–20MB、输出比例为 1:1 或 3:4；推荐尺寸分别为 1440×1440 和 1440×1920，同一坑位使用统一比例且包含 3–9 张。第三阶段需要展示原图事实并帮助用户选择，第四阶段负责生成和确认输出，第五阶段必须按实际文件执行最终校验。

## Goals / Non-Goals

**Goals:**

- 让每张第三阶段候选都具有可审计的原图大小、尺寸、比例、格式和身份信息。
- 在第三阶段准确区分硬阻断、推荐警告、可裁剪、可压缩和组合处理。
- 使用项目已有 Pillow 依赖实现本地、可部署、无外部服务的图片压缩。
- 支持直接、裁剪、压缩及裁剪并压缩四种合规输出链路。
- 在第四阶段清楚对比原图与处理后结果，在第五阶段重新校验实际文件。
- 兼容历史任务，通过重新检查原文件补齐数据，不伪造未知值。

**Non-Goals:**

- 不实现 AI 裁剪、生图、扩图、超分辨率或内容质量评分。
- 不自动替用户批准裁剪框或处理输出。
- 不修改或整理共享盘源文件。
- 不处理视频素材。
- 不以制造无意义元数据或填充字节的方式把小于 200KB 的图片伪装为合规。

## Decisions

### 1. 把原图事实与处理结果建模为两个不可混淆的结构

候选记录新增稳定的 `source_inspection`，至少包含路径、格式、`size_bytes`、EXIF 纠正宽高、数值比例、展示比例、SHA-256、检查时间和错误。针对 1:1/3:4 的最大内接尺寸与推荐状态存入 `target_assessments`。

第四阶段使用独立 `processed_output`，包含派生路径、大小、宽高、比例、格式、质量、SHA-256、动作、处理参数和提供方版本。页面始终用“原图”和“处理后”标签展示，不用同一字段在处理后覆盖原图数据。

备选方案是继续向候选顶层零散添加字段。该方案兼容改动较少，但很容易在裁剪或压缩后把输出数据误认为原图数据，因此不采用。

### 2. 预检在候选池生成时完成，历史数据按需重建

新候选生成时对最多 100 张当前候选执行文件 stat、Pillow 头部解析、EXIF 方向处理和 SHA-256。结果随第三阶段 review context 持久化，翻页和“换一批”不重复读取共享盘。

历史候选缺字段时进入“需要重新检查”状态，由 Agent 对当前候选重建 review context；不可访问文件得到明确阻断原因。不会用昨天的元数据猜测文件大小或比例。

为控制共享盘成本，实现可复用检查缓存，缓存键使用规范化路径、文件大小和修改时间；命中后仍保留来源信息。SHA-256 是最终身份依据，第四阶段处理前会再次核对。

### 3. 可选性依据“能否形成合规输出”，而非只看原图比例

分类器先判断可读性、格式、最小文件大小，再对所有目标比例计算最大内接裁剪框。只有至少一个目标比例能产生宽高均不低于 720 的输出时，图片才满足尺寸硬门槛。推荐分辨率只产生警告。

大于 20MB 时检查当前任务压缩提供方的实际可用性。提供方可用则允许采用并标记压缩；不可用则阻断。这取代“接口存在便允许选择”的旧行为。

### 4. 首版使用 Pillow 实现压缩

Pillow 已是项目依赖，适合当前 MVP，且不要求每台电脑额外安装 ImageMagick 或 libvips。压缩流程为：

1. 打开源图并应用 `ImageOps.exif_transpose`；
2. 如存在确认裁剪框，先裁剪；
3. 按策略背景色合成透明通道并转换为 RGB；
4. 先以策略最高质量（默认 92）、`optimize=True`、`progressive=True` 输出 JPEG；
5. 超过最大字节数时，在策略质量区间内搜索满足限制的最高质量；
6. 最低质量仍超限时按比例逐步缩小尺寸，再重复质量搜索，但不得低于最小宽高；
7. 生成后重新读取文件，校验大小、宽高、比例和 SHA-256。

接受边界仍是 20MiB；实现可使用低于上限的安全目标以避免上传端差异，但不得把 19MiB 错误显示为平台硬上限。若最高质量输出低于 200KB，不通过填充文件处理，而是返回不可发布状态。

未来大量并发或超大图吞吐成为瓶颈时，可以在同一 `ImageCompressionProvider` 契约下加入 pyvips 实现，不改变 UI 和审计模型。

### 5. 压缩与裁剪组成单一确定性处理流水线

第四阶段不先永久生成一个裁剪文件再读取它压缩，而是从已验证的源图片开始，在一次处理流水线中应用裁剪和压缩，最后只保存需要审查的派生输出。动作根据实际发生的步骤记录为 `crop`、`compress` 或 `crop_and_compress`。

派生文件名由源 SHA-256、策略 SHA-256、目标比例、裁剪框和压缩参数的稳定摘要组成。相同输入可安全复用任务目录内的结果；任何输出必须通过现有派生目录边界检查。

### 6. 源文件保护采用处理前后身份核对

处理开始前记录源路径的大小、修改时间和 SHA-256，完成后再次读取这些属性。若源 SHA-256 在处理期间变化，则废弃派生结果并要求重新检查。系统从不以写入模式打开源图片。

派生文件只允许写入当前时间戳任务的第四阶段目录。输出路径越界、符号链接/重解析后越界或源输出同路径均被拒绝。

### 7. 第四阶段确认与第五阶段校验分离

第四阶段负责让用户比较原图和输出并确认，但其确认不是对任意路径的永久信任。第五阶段按当前第三阶段 revision、策略 SHA-256、第四阶段确认状态及输出 SHA-256重新验证实际文件。

每坑 3–9 张、比例一致和文件硬门槛全部在服务端校验；浏览器预校验只用于及时提示，不能替代服务端判断。

### 8. 原因码保持稳定并面向恢复

新增或统一使用：

- `SOURCE_UNREADABLE`
- `SOURCE_METADATA_MISSING`
- `IMAGE_SIZE_BELOW_MINIMUM`
- `IMAGE_SIZE_EXCEEDED`
- `OUTPUT_DIMENSIONS_BELOW_MINIMUM`
- `COMPRESSION_UNAVAILABLE`
- `COMPRESSION_TARGET_UNREACHABLE`
- `OUTPUT_SIZE_BELOW_MINIMUM`
- `OUTPUT_IDENTITY_MISMATCH`
- `OUTPUT_PATH_OUTSIDE_TASK`

JSON 保存原因码和可读中文文案；Agent 依赖原因码恢复，页面显示文案。

## Risks / Trade-offs

- **共享盘上读取 100 张图片并计算 SHA-256 可能较慢** → 使用路径、大小和修改时间驱动的增量检查缓存，页面展示扫描进度，最终处理前再核验 SHA-256。
- **JPEG 转换会丢失透明通道** → 背景色由任务策略明确配置并记录；需要保留透明的格式不进入 JPEG 压缩路径。
- **Pillow 对超大图的内存占用较高** → 限制单图像素数、逐张处理、及时关闭对象；达到限制时给出明确错误，不并行加载整批原图。
- **压缩后可能低于 200KB** → 先保留最高允许质量；仍低于下限则阻断，不制造虚假文件体积。
- **文件修改时间缓存可能漏掉极端的同尺寸同时间替换** → 第四阶段与第五阶段仍以 SHA-256 做最终身份校验。
- **历史任务的原共享盘文件已经移动或离线** → 保留候选审计记录并明确标记不可读取，不使用旧缩略图冒充可发布原图。
- **从“超限均可选”改为“压缩可用才可选”会改变旧任务体验** → 历史任务重新预检并显示原因；默认部署 Pillow 提供方后正常可处理图片仍可选择。

## Migration Plan

1. 扩展任务级图片策略 Schema 和默认策略，保留旧策略加载时的明确迁移错误。
2. 扩展候选预检模型、检查缓存和第三阶段卡片，先为新任务启用。
3. 为历史任务加入按需重建命令和页面状态，验证当前真实任务能显示原图大小与比例。
4. 实现并注册 Pillow 压缩提供方，再启用超限图片的条件可选逻辑。
5. 扩展第四阶段处理动作、原图/输出对比和审计数据。
6. 最后启用第五阶段实际文件强校验，并执行全量 dry-run 与浏览器验收。

回滚时可停用 Pillow 提供方并恢复到只允许无需压缩的图片；已生成派生文件及审计 JSON 保留在任务目录，不回写共享盘。旧版不能理解的新 revision 不得静默提交。

## Open Questions

无。首版固定使用 Pillow 本地压缩；AI 裁剪继续保留接口但不实现。
