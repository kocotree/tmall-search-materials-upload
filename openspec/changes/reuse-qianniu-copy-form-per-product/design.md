## Context

参见 [proposal.md](proposal.md) 和 [product-scoped-qianniu-copy-session spec](specs/product-scoped-qianniu-copy-session/spec.md)。当前浏览器函数虽然接受多个坑位，但持久化处理器为保留逐坑位重试和 checkpoint，每次只传入一个坑位；浏览器函数又在每次调用后返回商品列表，因此同商品会重复搜索、开表单和等待 SPA 水合。

既有千牛表单能通过“上传图片”重新进入素材选择器。生产选择原语会取消既有勾选、只选择短唯一名称对应的新本地上传图片并确认，因此可以在不提交表单的情况下替换触发图片。首次生成动作通常为“AI生成文案”，已有结果后则需要“重新生成”。

## Goals / Non-Goals

**Goals:**

- 正常路径按商品复用一个已验证的发布表单。
- 保持重试、跳过、请求恢复、逐坑位进度和响应顺序完全兼容。
- 对坑位间图片和 AI 结果建立显式隔离，拒绝无法证明属于新生成周期的旧结果。

**Non-Goals:**

- 不批量生成一份文案供多个坑位共用。
- 不改变每坑使用第一张最终输出图的规则。
- 不改变千牛生成内容、文案字段、人工编辑、dry-run、批准或发布流程。
- 不增加另一套 Playwright 脚本或外部依赖。

## Decisions

### 1. 浏览器模块提供商品级会话，处理器保留逐坑位控制权

在既有 `qianniu_copy` 模块内引入商品级会话对象。会话在首次待处理坑位前搜索一次商品、读取并校验全部目标空坑位、打开一个表单；随后暴露逐坑位生成方法，最后统一退出未确认表单。

重试循环和 `progress.json` 仍留在持久化处理器。相比把整组坑位一次性交给旧函数，这能继续在每坑成功后 checkpoint、检查请求是否被 supersede，并只重试或跳过当前坑位。

### 2. 执行按商品分组，结果仍按原请求顺序投影

处理器按商品首次出现顺序构建稳定分组，只为仍未从 progress 恢复的坑位创建商品会话。完成结果继续写入以 `slot_id` 为键的映射，现有 `ordered_completed()` 按原 `slots` 数组投影，因此浏览器执行顺序变化不会改变 API、进度和响应顺序。

### 3. 每坑位重新选择唯一种子图并区分首次生成与重新生成

商品会话对每个坑位都重新复核本地输出 SHA-256、使用短唯一名称上传，并让素材选择器最终只确认一张当前图片。首坑优先点击“AI生成文案”；后续坑位在已有结果时点击“重新生成”。

重新生成前保存上一坑位结果。只有观察到“生成中”周期，或者结果内容相对上一坑位发生变化，才接受新结果；两者都无法证明时返回稳定的可恢复错误，防止旧文案误绑到新坑位。生成内容完全相同时，只要页面明确经历新生成周期仍允许接受。

### 4. 正常槽位之间不导航，异常恢复允许失效后重开

成功坑位之间始终复用当前表单。可恢复错误重试时先检查当前表单仍然存在并锁定同一商品；仍有效则在原表单重选图片并重试。只有 frame 已失效或页面自行退出时，才允许作为异常恢复重新搜索商品并打开表单。批次级安全异常继续直接停止。

这种策略优先满足正常路径只开一次，同时不牺牲现有网络和 SPA 异常重试能力。

## Risks / Trade-offs

- [千牛不同版本在换图后可能自动清空 AI 面板，也可能保留旧结果] → 同时兼容“AI生成文案”和“重新生成”，并通过生成周期或结果变化证明新结果。
- [同商品处理期间空坑位被外部修改] → 打开表单前一次性校验本商品全部目标位置；正式发布仍执行既有实时空坑位复查。
- [某坑位异常留下半完成素材选择器] → 重试前重新定位表单与素材选择器；无法恢复时使商品会话失效并仅走既有可恢复错误路径。
- [按商品分组改变执行顺序] → 所有持久化与响应继续按原请求顺序投影，`slot_id` 身份和 checkpoint 不变。

## Migration Plan

1. 先增加商品级会话与单元测试，保留旧批量函数作为兼容包装。
2. 将持久化处理器改为按商品创建会话，但继续使用原逐坑位 retry/skip/checkpoint 代码。
3. 更新 canonical Skill 和操作指南，重新生成 Skill 发现入口。
4. 发布新 Plugin 版本后只对新发起或重新生成的文案请求生效；已有 `progress.json` 继续按 `slot_id` 恢复，不迁移历史文件。

回滚时恢复逐坑调用包装函数即可；请求、进度和响应结构没有变化。
