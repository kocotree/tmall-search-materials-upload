## Context

参见 [proposal.md](proposal.md)。第三阶段后端已有两个不同入口：文件夹确认调用本机 `prepare-gallery` 路径，最终选图调用阶段提交并创建 handoff；但前端复用了页面底部的单一提交按钮和交接状态区域。本机 Worker 当前把成功检查数量写入 `prepared_count`，完成后再按商品与 SHA-256 去重，导致运行进度和最终候选数采用了不同口径。

文件夹索引目前只保存目录元数据。候选卡片在第一次画廊加载前没有图片数量；已完成的画廊结果则已经包含采用文件夹的原始发现数、排除父子路径重叠后的发现数和抽样数。真实 NAS、RaiDrive、Windows 会话身份和长时间页面交互不适合由自动化测试代替人工验收。

## Goals / Non-Goals

**Goals:**

- 让按钮位置、文案、请求路径和持久化证据共同证明“文件夹确认是本机操作，最终选图才交给 Codex”。
- 在不读取图片内容的前提下异步提供所有候选文件夹的原始素材数。
- 建立从路径发现、抽样检查到 SHA-256 去重后的统一计数模型和可验证不变量。
- 保持现有任务隔离、稳定抽样、画廊身份和最终 handoff 校验边界。
- 将自动化验证限制为简单、稳定的单元/接口/状态/静态页面契约，将复杂真实交互交由用户验收。

**Non-Goals:**

- 不在文件夹审查阶段生成预览、读取尺寸、计算 SHA-256 或判断图片内容是否重复。
- 不建立全量图片数据库，不修改共享 NAS 原图，也不改变每商品最多检查 100 张的策略。
- 不引入 AI 选择文件夹、图片、坑位或裁剪。
- 不自动操作真实 NAS 登录、网络盘映射、Windows 文件夹选择窗口或生产浏览器完成复杂端到端测试。

## Decisions

### 1. 使用两个物理上独立的按钮和请求路径

文件夹审查组件内部新增本机按钮，位于文件夹列表和画廊区域之间。该按钮直接调用本机 `prepare-gallery` API；文件夹审查步骤隐藏页面底部通用提交按钮。画廊完成并进入图片选择后，页面底部才显示“确认选图并提交给 Codex”。

不继续复用同一个按钮：虽然根据 `workflow_step` 切换标签和 API 在逻辑上可行，但按钮始终位于“交接状态”页脚，并被通用的 Agent 文案控制，用户无法可靠判断是否会产生 handoff。

### 2. 文件夹素材数使用任务级异步元数据计数

页面先立即展示候选文件夹，再由本机受控 Worker 对本任务的候选文件夹执行有界并发计数。结果按稳定 `folder_id + source_system + normalized folder_path` 写入任务级计数文档，至少包含状态、原始递归图片数、完成时间和稳定错误码。

计数器只枚举受支持图片扩展名和必要文件元数据，不打开文件。父文件夹的递归数量天然包含子文件夹，卡片明确称为“原始递归素材数”。选择确认后，gallery job 已有的路径去重与抽样统计覆盖对应卡片；SHA-256 内容去重完成后再补充“最终唯一候选数”。

不把计数加入机器级共享文件夹索引：这会显著扩大索引刷新成本并产生跨任务陈旧语义。也不阻塞文件夹审查首屏等待全部计数完成。

### 3. 用显式计数字段替代 `prepared_count` 多义字段

gallery job 的进度和完成结果采用以下字段：

- `discovered_path_count`：采用文件夹中发现且完成路径去重的图片路径数。
- `planned_inspection_count`：确定性抽样后计划检查的图片数，最多为商品数乘以 100。
- `inspected_count`：已成功完成基础检查和 SHA-256 的数量。
- `inspection_failure_count`：检查抛错或不可读取的数量。
- `content_duplicate_count`：按商品 SHA-256 去除的重复内容数量。
- `final_candidate_count`：最终写入画廊的唯一候选数量，包括可展示但预检不可选的候选。

兼容期可继续输出旧字段，但前端只使用新字段。完成时满足：

`inspected_count = final_candidate_count + content_duplicate_count`

并且：

`planned_inspection_count = inspected_count + inspection_failure_count + pending_count`

完成状态的 `pending_count` 必须为 0。商品级统计使用同一口径，所有商品的最终候选数之和必须等于批次最终候选数。

### 4. 在处理过程中按商品维护内容去重统计

检查成功后立即按 `(product_id, sha256)` 维护稳定的已见集合，因此可以持续更新唯一候选数和内容重复数。最终画廊仍按现有确定性排序生成，不改变相同输入的稳定输出。跨商品相同 SHA-256 不在本步骤互相删除，因为每个商品的候选边界独立；最终用户选图时继续执行任务级唯一性约束。

不等到 `build_gallery_data` 完成后才推断差额：那会让运行期无法提供准确的重复数，也会继续造成“检查 300、最终 286”缺少解释。

### 5. 完成结果是页面的唯一最终计数来源

Worker 在写入候选结果后，以同一最终快照更新 job 状态和统计。前端检测到 `running → completed` 时重新加载阶段结果并清除运行消息；刷新时也从完成结果重建文案。不得把最后一次轮询的运行文本保留在操作消息区域。

### 6. 自动化与人工验收分层

自动化只验证：

- 本机按钮请求不会创建 handoff，最终提交才创建一个 handoff。
- 计数器不打开图片内容，并正确处理成功、拒绝访问和超时。
- 计数不变量、商品内 SHA 去重以及 `300 → 286` 等固定数据场景。
- 页面静态结构、按钮可见性、标签和运行/完成状态渲染。
- 状态刷新后不保留陈旧运行文案。

用户负责真实 NAS/RaiDrive、Windows 身份、加载耗时、原生窗口、刷新/中断恢复以及连续人工点击等复杂交互验收。实现阶段不以自动运行这些复杂场景作为完成前置条件。

## Risks / Trade-offs

- [候选文件夹异步计数仍会产生大量 NAS 元数据访问] → 首屏不等待计数；使用低并发、单文件夹超时和可取消任务，并显示独立计数状态。
- [父子文件夹递归数量看似重复] → 明确标注“原始递归素材数”，加载后再显示排除路径重叠后的本轮发现数。
- [旧会话只有 `prepared_count`] → 前端兼容读取旧字段但标记为“历史进度”；新 Worker 必须输出新计数模型。
- [运行中去重集合增加少量内存] → 每商品最多检查 100 张，集合规模有严格上限。
- [本机按钮和页脚按钮分离后状态控制重复] → 共享最小的可用性判定函数，但保持 DOM 控件和事件处理独立。

## Migration Plan

1. 先扩展 gallery job 和文件夹计数文档，保留旧字段兼容读取。
2. 增加本机按钮和文件夹计数展示，移除文件夹阶段页脚提交按钮及 Agent 文案。
3. 切换进度渲染到新字段，并验证完成快照替换运行文本。
4. 更新 Skill 和运维说明中的第三阶段按钮、计数与测试边界。
5. 用户使用真实会话验收文件夹计数、按钮位置、长时间加载及最终交接。

回滚时可恢复旧前端渲染并继续读取兼容字段；不得回滚最终 handoff 的身份校验或删除已有任务证据。
