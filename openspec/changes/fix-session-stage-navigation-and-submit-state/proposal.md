## Why

历史任务通过仅含 `session_id` 的链接重新打开时，前端固定停留在第一阶段，而不是会话记录的 `current_stage`。已完成阶段又会锁定保存与提交按钮，造成用户点击“保存草稿”或“提交给 Agent”没有反应；进入当前阶段后，页面初始化还会误触发自动保存，并可能静默吞掉保存期间发生的提交点击。

## What Changes

- 打开已有任务时，以服务端 `session.current_stage` 作为默认活动阶段；只有该阶段无效时才回退到第一阶段。
- 首次加载时同步全部阶段的真实 revision 与状态，避免导航栏把已完成阶段错误显示为“待填写”。
- 已完成、已提交或处理中阶段明确显示锁定原因和下一步入口，不再让禁用按钮表现得像可操作按钮。
- 区分“数据水合/组件初始化”和“用户编辑”：初始化隐藏字段、默认坑位或图片决定时不得触发 dirty 状态、自动保存或新 revision。
- 保存请求进行期间接收到用户提交意图时，不得静默丢弃；应排队在保存完成后提交，或给出明确且可恢复的提示。
- 为历史任务恢复、初始化幂等、保存与提交竞态增加前端及服务端回归测试。

## Capabilities

### New Capabilities

- `session-stage-navigation-and-persistence`: 规定历史任务恢复时的当前阶段选择、全阶段状态同步、初始化无副作用以及保存/提交竞态处理。

### Modified Capabilities

无。

## Impact

- 前端：`interaction/static/app.js`、`ui-state.js`、阶段导航、表单水合、自动保存与提交状态管理。
- 服务端：会话与阶段状态 API 的响应契约可能需要补充统一的阶段状态快照，但不改变现有任务目录格式。
- 测试：前端状态测试、交互 API 测试和真实浏览器历史任务恢复验收。
- 数据兼容性：不迁移现有任务；现有 `session.json` 的 `current_stage`、revision 和 status 继续作为事实来源。
