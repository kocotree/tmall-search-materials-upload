# 天猫搜推素材业务系统交接说明书

## 1. 文档目的

本文用于把“空坑位定时通知 + 搜推素材上传”完整业务系统交接给后续开发、运维和业务支持人员。交接完成的标准不是代码能够运行，而是维护人员能够完成环境配置、版本发布、用户安装、定时巡检、故障恢复和业务验收，普通运营人员能够按照工作台提示完成上传。

用户侧图文操作手册见：[上传搜推素材插件使用文档](上传搜推素材插件使用文档/上传搜推素材插件使用文档.md)。

## 2. 系统组成与边界

系统由两个独立仓库组成：

| 项目 | 公司仓库 | 生产分支 | 作用 | 使用者 |
|---|---|---|---|---|
| 上传搜推素材 Plugin | `https://github.com/kocotree/tmall-search-materials-upload.git` | `win` | 巡检、素材匹配、选图、坑位编排、文案生成、上传及成功记录 | 运营用户、Plugin 维护者 |
| 空坑位定时通知 | `https://github.com/kocotree/tmall-empty-slot-notifier.git` | `main` | 定时调用 Plugin 的公开命令巡检空坑位，并在飞书群通知负责人 | 运维人员 |

两个项目必须保持解耦。通知项目不得复制或导入 Plugin 的 Python 内部模块，只能调用 Plugin 对外公开的 `scripts\run-plugin.cmd`。这样 Plugin 可以独立升级，通知任务只依赖稳定的命令契约。

完整业务链路：

```text
Windows 计划任务
  → 通知项目调用 Plugin 只读巡检
  → 读取飞书商品负责人和产品等级
  → 汇总空坑位并通知“打爆款小分队”
  → 负责人在 Codex 中启动上传 Plugin
  → 工作台巡检并选择待补商品
  → 匹配 NAS 素材、选图、裁剪和生成文案
  → 用户确认后批量上传千牛
  → 每个成功坑位异步写入飞书上传记录表
```

## 3. 生产环境前置条件

### 3.1 公共条件

- Windows 11，使用同一个日常登录的桌面用户安装和运行。
- 已安装并登录 Codex 桌面应用。
- 已安装 Git for Windows，并能通过 HTTPS 访问公司 GitHub。
- 公司网络可以访问千牛、飞书以及两台 NAS。
- 千牛目标店铺账号可登录素材中心，账号具备查看和发布搜推素材的权限。
- Windows 用户已经在资源管理器中完成 NAS 身份验证；项目不保存 NAS 用户名或密码。
- 自动化期间使用 Plugin 管理的专用浏览器会话，不要关闭该浏览器或在其中进行无关操作。

Plugin 默认识别以下素材目录，实际以当前电脑可访问的映射盘或 UNC 路径为准：

- `Y:\视觉部\1-模特图`
- `Z:\浙江酷趣\运营中心\营销板块\小红书koc置换&买家秀\优质买家秀`
- `Z:\浙江酷趣\运营中心\营销板块\小红书koc置换&淘宝买家秀\优质买家秀`
- `Z:\浙江酷趣\素材共享库\01 小红书`
- `Z:\浙江酷趣\素材共享库\02 天猫买家秀`

任务数据使用稳定的 `source_id + relative_path`，不把某台电脑的盘符当作跨电脑身份。团队文件夹索引应放在共享盘约定位置；索引只保存目录元数据，不保存 NAS 凭据。

### 3.2 飞书应用与机器人

当前系统使用团队飞书应用“天猫素材坑位巡检助手”，公开 App ID 为 `cli_aa07506f94785beb`。App Secret、访问令牌和用户授权令牌不得写入 Git、文档或 Codex 对话。

飞书身份分为两类：

1. **Plugin 用户身份**：运营用户在工作台点击“授权飞书”，用于读取商品信息、获取当前上传负责人姓名以及新增成功上传记录。
2. **通知项目机器人身份**：计划任务使用应用机器人读取商品信息、读取目标群和群成员，并以机器人身份发送通知。机器人身份不依赖运营用户的网页登录状态；执行 `lark-cli auth logout` 只退出本机用户身份，不会删除已经配置好的机器人身份。

Plugin 用户授权所需 scope：

- `wiki:node:read`
- `base:block:read`
- `base:field:read`
- `base:record:read`
- `base:record:create`

通知机器人需要在飞书开发者后台开放以下能力：

- 读取商品信息 Base 的字段和记录；至少包含 `base:record:read`，并开放对应 Base 结构读取能力。
- 搜索机器人可见群聊。
- 读取目标群成员，用于把业务负责人映射为飞书原生 @。
- 以应用机器人身份向群聊发送消息。

配置要求：

1. 在飞书开放平台创建或接管企业自建应用，启用机器人能力。
2. 开通上述权限并发布一个对公司成员可用的应用版本。
3. 把机器人加入“打爆款小分队”。
4. 给机器人授予商品信息表只读权限。
5. 给运营成员授予商品信息表查看权限，以及上传记录表“查看 + 新增记录”权限。
6. 在通知任务所在电脑使用 `lark-cli config init --new` 配置 App ID 和 App Secret；凭据只保存在该 Windows 用户的 lark-cli 安全配置中。
7. 在普通用户电脑上不分发 App Secret。Plugin 会使用公开 App ID 发起用户授权，用户在飞书官方页面完成授权。

如果后台新增了 scope，必须先在飞书开放平台发布新应用版本，再让用户重新授权。只在代码里增加 scope 不会自动获得飞书权限。

|---|---|---|

### 3.4 千牛与浏览器

- 素材中心：<https://myseller.taobao.com/home.htm/material-center/material-management?tab=recommend>
- Plugin 和通知任务默认使用本机 CDP 地址 `http://127.0.0.1:9222`。
- 登录失效时允许用户在官方登录页手动登录；滑动验证必须由用户完成，程序不得绕过。
- 店铺身份不一致、发布结果不确定、人机验证或任务身份异常必须停止批次，不能作为普通坑位失败跳过。
- 千牛页面结构变化后，应先更新并验证 `selectors.local.yaml`，禁止把“未找到元素”解释为“没有空坑位”。

## 4. 上传 Plugin 的开发、发布与用户交付

### 4.1 开发人员获取项目

```powershell
git clone https://github.com/kocotree/tmall-search-materials-upload.git
cd tmall-search-materials-upload
git checkout win
```

开发只面向 Windows 11。根目录 `AGENTS.md`、`SKILL.md` 和 `harness-docs/Plugin 发布与测试流程.md` 是维护约束；修改 Skill 前必须同步 `skills/upload-search-materials/SKILL.md` 的发现入口。

建议的代码级验证：

```powershell
uv sync
uv run python -m pytest -q
node --check src/upload_search_materials/interaction/static/app.js
uv run python -m compileall -q src
uv run python scripts/validate_skill_entry.py --repository-root .
git diff --check
```

真实千牛登录、页面交互和生产上传只能由业务人员手工验收，自动测试不得发送飞书消息或执行真实发布。

### 4.2 Plugin 发布规则

1. 所有代码、文档和测试修改完成后先运行验证。
2. 最后修改 `.codex-plugin/plugin.json`，生成从未使用过的新版本号，例如 `0.1.0+codex.YYYYMMDDHHMMSS`。
3. 版本号生成后，任何随 Plugin 分发的文件再次变化都必须重新生成新版本号。
4. 提交并推送 `win` 分支。
5. 核对 GitHub `win` 指向本地提交，并核对远程 manifest 版本号。
6. 不允许用相同版本号覆盖不同代码；Codex Plugin 缓存会按版本复用。

### 4.3 开发人员把 Plugin 交给用户

公司 GitHub 仓库是源码维护仓库，也是普通用户安装 Plugin 的 HTTPS 分发源。普通用户不需要克隆源码或手工安装 Python。

首次安装时，让用户在 Codex 新任务中发送：

```text
请帮我安装“上传天猫搜推素材”的 Plugin，安装命令是：
codex.cmd plugin marketplace add https://github.com/kocotree/tmall-search-materials-upload.git --ref win --json
codex.cmd plugin add tmall-search-materials@tmall-materials-team --json
请完成团队插件来源添加、安装和启用，并运行 codex.cmd plugin list --json 检查状态，告诉我安装是否成功、当前版本号和来源分支。
```

验收必须确认：

- Plugin ID 为 `tmall-search-materials@tmall-materials-team`。
- `installed=true`、`enabled=true`。
- Marketplace 来源为公司 GitHub。
- `source.ref=win`。
- 安装版本与 GitHub `win` 的 `.codex-plugin/plugin.json` 一致。

从旧 Gitee 来源迁移时，必须先结束旧工作台，然后移除旧 Plugin 和 Marketplace，再用 GitHub 地址重新添加。完整命令见用户使用文档。

正常升级流程：

```powershell
codex.cmd plugin marketplace upgrade tmall-materials-team --json
codex.cmd plugin remove tmall-search-materials@tmall-materials-team --json
codex.cmd plugin add tmall-search-materials@tmall-materials-team --json
codex.cmd plugin list --json
```

升级成功不代表旧工作台已经热更新。必须结束旧工作台，并从新安装版本重新启动；恢复历史任务时复用原 session ID 和 runs 数据，但 `project_root` 必须指向新 Plugin 版本。

### 4.4 用户首次使用流程

1. 用户确认 Windows 资源管理器可以访问 NAS。
2. 在 Codex 新建任务，输入“使用插件完成搜推素材上传”。
3. 首次启动由 Plugin 自动准备 `%LOCALAPPDATA%\tmall-search-materials\runtime`，用户不需要手工配置 Python。
4. 在工作台完成飞书授权；后续任务复用当前 Windows 用户授权，失效时重新授权。
5. 登录千牛目标店铺并保持专用浏览器开启。
6. 检查团队索引和五个默认图片源，按需增加或删除图片源。
7. 完成度巡检后选择待补坑位。
8. 核对候选文件夹、加载并选择素材。
9. 检查坑位编排、裁剪结果、标题和描述。
10. 在上传确认页核对任务并提交。
11. 在结果页及飞书上传记录表检查成功、跳过和失败项。
12. 点击“结束当前任务”，或等待结果保留期结束后自动关闭工作台。

## 5. 定时通知项目部署

### 5.1 获取代码

```powershell
git clone https://github.com/kocotree/tmall-empty-slot-notifier.git
cd tmall-empty-slot-notifier
uv sync
Copy-Item config.example.json config.local.json
```

`config.local.json`、`state/`、`runs/` 和 `result.md` 均为本机数据，已经被 `.gitignore` 排除，禁止提交。

### 5.2 配置 `config.local.json`

| 配置项 | 说明 |
|---|---|
| `plugin_root` | Plugin 开发目录或已安装版本根目录；必须包含 `scripts\run-plugin.cmd` |
| `store` | 千牛目标店铺名称，必须与登录身份一致 |
| `products_csv` | Plugin 完整度计算使用的商品 CSV |
| `selectors_file` | 已验证的生产选择器，通常为 `%LOCALAPPDATA%\tmall-search-materials\config\selectors.local.yaml` |
| `cdp_url` | 专用千牛浏览器地址，默认 `http://127.0.0.1:9222` |
| `product_base_token` | 天猫商品信息表 Wiki 节点解析出的真实 Base token，不是 Wiki token |
| `product_table_id` | 当前为 `tblRr3NI24dvfwZ4` |
| `product_snapshot` | 本项目商品快照，建议 `state\product-metadata-snapshot.json` |
| `lark_cli` | `lark-cli.cmd` 或原生程序的绝对路径 |
| `chat_name` | 目标群，当前为“打爆款小分队” |
| `owner_member_names` | 业务负责人名称到群成员显示名或唯一 `姓名&业务昵称` 后缀的映射 |
| `chat_id`、`owner_mentions` | 由配置命令自动写入，不手工填写 |

若 `plugin_root` 指向 Codex 的带版本安装缓存，Plugin 每次升级后路径会变化，运维人员必须更新该配置。长期计划任务更适合指向经过验收、固定检出的 `win` 工作目录，并在升级时由维护者统一更新和回归。

### 5.3 绑定飞书群和负责人

先确认 lark-cli 的机器人身份可用，再执行：

```powershell
lark-cli auth status --json --verify
.\configure-lark.ps1
```

配置命令会精确搜索“打爆款小分队”、读取完整群成员列表，并写入稳定的 `chat_id` 和 `owner_mentions`。群名匹配不唯一、成员列表不完整、负责人无法唯一匹配时会停止配置，不能手工猜测 ID。

新增负责人、成员改名或群成员变化后，需要更新 `owner_member_names` 并重新运行 `configure-lark.ps1`。

### 5.4 验证与正式运行

先运行单元测试：

```powershell
$env:PYTHONPATH = ".\src"
uv run python -m unittest discover -s tests -v
```

再运行不发消息的完整演练：

```powershell
.\run-notifier.ps1 -DryRun
```

演练会访问千牛和飞书商品表，但不会发消息，也不会更新通知状态。核对输出无误后，才执行真实运行：

```powershell
.\run-notifier.ps1
```

真实运行规则：

- 每次先完整分页更新商品信息快照；刷新失败时保留上次成功快照。
- 汇总为 0 时不发消息，但更新观察状态。
- 非零结果与上次完全相同时不重复通知。
- 负责人总数、等级分布或未分配商品集合变化时才发送新消息。
- 发送失败不会把本次结果标记为已经成功通知，下次仍可重试。
- 同一时间只允许一个实例运行；4 小时内的锁会阻止重复启动。

### 5.5 Windows 计划任务

在“任务计划程序”中创建仅供该业务使用的任务：

- 使用部署项目和登录千牛的同一个 Windows 用户。
- 选择“仅当用户登录时运行”，因为登录恢复和页面自动化需要交互桌面。
- 触发时间使用北京时间，按业务要求设置工作日频率。
- 程序：`powershell.exe`
- 参数：`-NoProfile -ExecutionPolicy Bypass -File "<项目目录>\run-notifier.ps1"`
- 起始位置：通知项目根目录。
- 避免并行启动同一任务；失败时可以延迟重试，但不要高频循环。

电脑休眠、Codex/专用浏览器退出、千牛登录过期、飞书机器人权限撤销都会影响计划任务。运维应定期查看任务计划程序历史、项目 `runs/` 和 `state/notification-state.json`。

## 6. 数据、缓存与清理

### 上传 Plugin

- 用户级运行环境：`%LOCALAPPDATA%\tmall-search-materials\runtime`
- 任务数据：默认位于 `%LOCALAPPDATA%\tmall-search-materials\runs`
- 飞书本机快照：运行环境下的 `lark` 子目录
- Codex Plugin 缓存：`%USERPROFILE%\.codex\plugins\cache\tmall-materials-team\tmall-search-materials`

任务目录包含状态、日志、预览、裁剪结果和审计证据，长期使用会占用 C 盘。只能清理已经结束且无需审计恢复的旧任务，不得在任务运行中删除当前 session。

### 通知项目

- `runs/`：每次巡检的 CSV、checkpoint 和完整度矩阵。
- `state/product-metadata-snapshot.json`：上次完整成功的商品信息快照。
- `state/notification-state.json`：上次观察和成功发送签名。
- `result.md`：最近一次需要通知的本地文本结果。

清理通知状态会让系统把下一次非零结果视为首次结果并再次发送；执行前必须确认业务影响。

## 7. 常见故障与恢复

| 现象 | 优先检查 | 恢复原则 |
|---|---|---|
| 安装后仍是旧版本 | `plugin list` 的版本、来源和 `source.ref`；旧工作台路径 | 发布新版本号，重新安装并从新版本重启工作台 |
| Plugin 缓存拒绝访问/文件占用 | 旧工作台或 Codex 进程仍占用版本目录 | 先正常结束工作台，再移除 Plugin；不要递归删除不明确目录 |
| 飞书页面已授权但工作台未授权 | lark-cli 用户身份、App ID、scope 和实时状态兼容 | 重新点击授权；确认应用版本已发布且用户在可用范围内 |
| 通知机器人可用但用户未授权 | `identities.bot` 与 `identities.user` 是两套身份 | Plugin 用户单独授权；不要把 bot ready 当作用户已授权 |
| 上传记录没有立即出现 | 本机成功状态、后台队列证据、Base 新增权限 | 不重复上传；先恢复飞书写入并执行补齐 |
| NAS/索引不可用 | 同一 Windows 用户能否在资源管理器访问，盘符和 UNC 是否对应 | 先恢复 Windows 网络会话，再在配置页重新选择；不保存密码 |
| `PERSISTENCE_ACCESS_DENIED` | 当前 runs 目录权限、旧进程占用、防病毒软件 | 使用用户可写运行目录，结束占用进程；不要删除正在运行的任务 |
| 千牛找不到元素或刷新循环 | 登录状态、目标店铺、选择器和遮罩弹窗 | 先判断登录/风控，再更新选择器；不能把错误当作零数据 |
| 通知项目没有发消息 | 汇总是否为 0/未变化，机器人是否在群内，负责人映射是否完整 | 查看命令 JSON、`result.md` 和通知状态；不通过手工改状态强制发送 |
| C 盘持续增大 | Plugin runs、预览/裁剪输出、安装缓存和通知 runs | 仅清理已结束的旧任务与废弃版本缓存，并保留所需审计资料 |

## 8. 安全与权限边界

以下内容不得进入两个 GitHub 仓库：

- 飞书 App Secret、access token、refresh token、授权 device code。
- 千牛 Cookie、浏览器用户数据、账号和密码。
- NAS 账号、密码或 Windows 凭据。
- `config.local.json`、本机绝对安装缓存路径、运行状态和真实业务导出数据。
- 未脱敏的商品、成员、聊天 ID 或上传审计文件，除非公司已明确允许作为测试 fixture。

NAS 读取默认只读；真实上传只允许来自用户当前页面提交的精确任务清单。发布结果不确定、人机验证或店铺身份异常必须停止，不能通过扩大重试范围绕过安全门禁。

## 10. 维护建议

- 上传 Plugin 保持 `win` 为唯一 Windows 生产分支；功能开发使用短期分支，验收后合并发布。
- 通知项目保持独立部署，不把定时器、机器人凭据或通知状态放进 Plugin。
- 千牛页面变化时先更新选择器和回归测试，再发新版；不要在通知项目里复制临时选择器修复。
- 飞书表结构变更前先核对代码字段映射，并保留“原图 SHA-256”。
- 每次发布都同步更新用户文档、交接文档和版本验收记录。
