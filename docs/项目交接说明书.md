# 天猫搜推素材业务系统交接说明书

## 1. 项目进度和文档说明

**进度：**

-  定时巡检空坑位并通知到飞书群聊
-  运营人员使用搜推素材插件完成搜推素材的上传

**文档说明：**

本文档用于把“空坑位定时通知 + 搜推素材上传”完整业务系统交接给后续开发、运维和业务支持人员。交接完成的标准不是代码能够运行，而是维护人员能够完成环境配置、版本发布、用户安装、定时巡检、故障恢复，普通运营人员能够按照工作台提示完成上传。

用户侧图文操作手册见：[上传搜推素材插件使用文档](https://kocotree.feishu.cn/wiki/OOdEwnwNpi1cuFkUiQlcLbRKnGc?from=from_copylink)。

## 2. 系统组成与边界

系统由两个独立仓库组成：

| 项目                | 公司仓库                                                     | 生产分支 | 作用                                                      | 使用者                   | 分支说明                                                     |
| ------------------- | ------------------------------------------------------------ | -------- | --------------------------------------------------------- | ------------------------ | ------------------------------------------------------------ |
| 上传搜推素材 Plugin | https://github.com/kocotree/tmall-search-materials-upload.git | win      | 巡检、素材匹配、选图、坑位编排、文案生成、上传及成功记录  | 运营用户、Plugin 维护者  | main 分支是用来开发mac版本的，目前完成部分，后面可以基于win分支进行开发 |
| 空坑位通知程序      | https://github.com/kocotree/tmall-empty-slot-notifier.git    | main     | 由 Codex 定时任务调用，执行空坑位巡检并在飞书群通知负责人 | 运维人员、Codex 定时任务 | 无                                                           |

两个项目使用独立仓库并分别维护，但当前运行关系不是完全独立：通知项目在运行时单向依赖上传 Plugin。通知项目本身不包含千牛空坑位采集和完整度计算实现，而是通过上传 Plugin 对外公开的 `scripts\run-plugin.cmd`，依次调用 `supplement --scan-mode high-value` 和 `inspect-completeness`。因此，运行通知项目的电脑必须先安装并启用 `tmall-search-materials@tmall-materials-team`；如果 Plugin 未安装、被禁用、安装路径失效或公开命令发生不兼容变化，通知项目将无法完成巡检。

这里的“独立”仅表示两个仓库、发布流程、本机状态和职责边界相互分开，不表示通知项目能够脱离 Plugin 单独运行。依赖方向只有一条：通知项目依赖上传 Plugin，上传 Plugin 不依赖通知项目。

完整业务链路：

Codex 定时任务按计划触发

  → 运行通知项目

  → 通知项目调用上传 Plugin 的公开命令进行只读巡检

  → 读取飞书商品负责人和产品等级

  → 汇总空坑位并通知“打爆款小分队”

  → 负责人在 Codex 中启动上传 Plugin

  → 工作台巡检并选择待补商品

  → 匹配 NAS 素材、选图、裁剪和生成文案

  → 用户确认后批量上传千牛

  → 每个成功坑位异步写入飞书上传记录表

## 3. 生产环境前置条件

### 3.1 公共条件

- Windows 版本，使用同一个日常登录的桌面用户安装和运行。
- 已安装并登录 Codex 桌面应用。
- 已安装 Git for Windows，并能通过 HTTPS 访问公司 GitHub。
- 公司网络可以访问千牛、飞书以及两台 NAS。
- 千牛目标店铺账号可登录素材中心，账号具备查看和发布搜推素材的权限。
- Windows 用户已经在资源管理器中完成 NAS 身份验证；项目不保存 NAS 用户名或密码。
- 自动化期间使用 Plugin 管理的专用浏览器会话，不要关闭该浏览器或在其中进行无关操作。

Plugin 默认识别以下素材目录，实际以当前电脑可访问的映射盘或 UNC 路径为准：

- `Y:\视觉部\1-模特图`
- `Z:\浙江酷趣\运营中心\营销板块\小红书koc置换&买家秀\优质买家秀`
- `Z:\浙江酷趣\运营中心\营销板块\小红书koc置换&淘宝买家秀\优质买家秀`
- `Z:\浙江酷趣\素材共享库\01 小红书`
- `Z:\浙江酷趣\素材共享库\02 天猫买家秀`

任务数据使用稳定的 `source_id + relative_path`，不把某台电脑的盘符当作跨电脑身份。团队文件夹索引应放在共享盘约定位置；索引只保存目录元数据，不保存 NAS 凭据。

### 3.2 飞书应用与机器人

当前系统使用团队飞书应用“天猫素材坑位巡检助手”，公开 App ID 为 `cli_aa07506f94785beb`。App Secret、访问令牌和用户授权令牌不得写入 Git、文档或 Codex 对话。

飞书身份分为两类：

1. **Plugin 用户身份**：运营用户在工作台点击“授权飞书”，用于读取商品信息、获取当前上传负责人姓名以及新增成功上传记录。
2. **通知项目机器人身份**：Codex 定时任务运行通知项目时，程序使用应用机器人读取商品信息、读取目标群和群成员，并以机器人身份发送通知。机器人身份不依赖运营用户的网页登录状态；执行 `lark-cli auth logout` 只退出本机用户身份，不会删除已经配置好的机器人身份。

Plugin 用户授权所需 scope：

- `wiki:node:read`
- `base:block:read`
- `base:field:read`
- `base:record:read`
- `base:record:create`

通知机器人需要在飞书开发者后台开放以下能力：

- 读取商品信息 Base 的字段和记录；至少包含 `base:record:read`，并开放对应 Base 结构读取能力。
- 搜索机器人可见群聊。
- 读取目标群成员，用于把业务负责人映射为飞书原生 @。
- 以应用机器人身份向群聊发送消息。

配置要求：

1. 在飞书开放平台创建或接管企业自建应用，启用机器人能力。
2. 开通上述权限并发布一个对公司成员可用的应用版本。
3. 把机器人加入“打爆款小分队”。
4. 给机器人授予商品信息表只读权限。
5. 给运营成员授予商品信息表查看权限，以及上传记录表“查看 + 新增记录”权限。
6. 由运维人员在执行通知任务的电脑上完成一次 `lark-cli config init --new`，配置 App ID 和 App Secret；凭据只保存在该 Windows 用户的 lark-cli 安全配置中，不写入任务提示词或项目文件。
7. 在普通用户电脑上不分发 App Secret。Plugin 会使用公开 App ID 发起用户授权，用户在飞书官方页面完成授权。

如果后台新增了 scope，必须先在飞书开放平台发布新应用版本，再让用户重新授权。只在代码里增加 scope 不会自动获得飞书权限。

## 4. 上传 Plugin 的开发、发布与用户交付

### 4.1 开发人员获取项目

```Plain
git clone https://github.com/kocotree/tmall-search-materials-upload.git
cd tmall-search-materials-upload
git checkout win
```

win分支开发只面向 Windows用户的。根目录 `AGENTS.md`、`SKILL.md` 和 `harness-docs/Plugin 发布与测试流程.md` 是维护约束；修改 Skill 前必须同步 `skills/upload-search-materials/SKILL.md` 的发现入口。

建议的代码级验证：

```Plain
uv sync
uv run python -m pytest -q
node --check src/upload_search_materials/interaction/static/app.js
uv run python -m compileall -q src
uv run python scripts/validate_skill_entry.py --repository-root .
git diff --check
```

真实千牛登录、页面交互和生产上传只能由业务人员手工验收，自动测试不得发送飞书消息或执行真实发布。

### 4.2 Plugin 发布规则

1. 所有代码、文档和测试修改完成后先运行验证。
2. 最后修改 `.codex-plugin/plugin.json`，生成从未使用过的新版本号，例如 `0.1.0+codex.YYYYMMDDHHMMSS`。
3. 版本号生成后，任何随 Plugin 分发的文件再次变化都必须重新生成新版本号。
4. 提交并推送 `win` 分支。
5. 核对 GitHub `win` 指向本地提交，并核对远程 manifest 版本号。
6. 不允许用相同版本号覆盖不同代码；Codex Plugin 缓存会按版本复用。

### 4.3 开发人员把 Plugin 交给用户

公司 GitHub 仓库是源码维护仓库，也是普通用户安装 Plugin 的 HTTPS 分发源。普通用户不需要克隆源码或手工安装 Python。

首次安装时，让用户在 Codex 新任务中发送：

请帮我安装“上传天猫搜推素材”的 Plugin，安装命令是：

codex.cmd plugin marketplace add https://github.com/kocotree/tmall-search-materials-upload.git --ref win --json

codex.cmd plugin add tmall-search-materials@tmall-materials-team --json

请完成团队插件来源添加、安装和启用，并运行 codex.cmd plugin list --json 检查状态，告诉我安装是否成功、当前版本号和来源分支。

验收必须确认：

- Plugin ID 为 `tmall-search-materials@tmall-materials-team`。
- `installed=true`、`enabled=true`。
- Marketplace 来源为公司 GitHub。
- `source.ref=win`。
- 安装版本与 GitHub `win` 的 `.codex-plugin/plugin.json` 一致。

从旧 Gitee 来源迁移时，必须先结束旧工作台，然后移除旧 Plugin 和 Marketplace，再用 GitHub 地址重新添加。完整命令见用户使用文档。

### 4.4 用户首次使用流程

1. 用户确认 Windows 资源管理器可以访问 NAS。
2. 在 Codex 新建任务，输入“使用插件完成搜推素材上传”。
3. 首次启动由 Plugin 自动准备 `%LOCALAPPDATA%\tmall-search-materials\runtime`，用户不需要手工配置 Python。
4. 在工作台完成飞书授权；后续任务复用当前 Windows 用户授权，失效时重新授权。
5. 登录千牛目标店铺并保持专用浏览器开启。
6. 检查团队索引和五个默认图片源，按需增加或删除图片源。
7. 完成度巡检后选择待补坑位。
8. 核对候选文件夹、加载并选择素材。
9. 检查坑位编排、裁剪结果、标题和描述。
10. 在上传确认页核对任务并提交。
11. 在结果页及飞书上传记录表检查成功、跳过和失败项。
12. 点击“结束当前任务”，或等待结果保留期结束后自动关闭工作台。

用户侧图文操作手册见：[上传搜推素材插件使用文档](https://kocotree.feishu.cn/wiki/OOdEwnwNpi1cuFkUiQlcLbRKnGc?from=from_copylink)。

## 5. 定时通知项目的 Codex 部署与调度

### 5.1 正确理解项目角色

`tmall-empty-slot-notifier` 不是 Plugin，也不由普通运营用户安装。它是一个独立仓库中的确定性通知程序，负责调用上传 Plugin 获取空坑位结果、按负责人和产品等级汇总，并发送飞书群通知。它不能脱离上传 Plugin 单独完成千牛巡检。

定时能力由 Codex 桌面应用中的定时任务提供：

Codex 定时任务负责“何时运行”

  → tmall-empty-slot-notifier 负责“组织巡检、汇总和通知”

  → tmall-search-materials-upload Plugin 实际执行千牛只读采集和完整度计算

因此，开发人员交付给业务团队时只需要：

1. 由运维人员在 Codex 中保存通知项目。
2. 先让 Codex 完成项目拉取、环境配置和一次 dry-run。
3. dry-run 验收通过后，再让 Codex 为该项目创建定时任务。
4. 普通运营人员只接收群通知并使用上传 Plugin，不需要接触通知仓库、配置文件或定时任务。

通知项目的生产前置条件包括：上传 Plugin 已安装并启用、Plugin 的 `scripts\run-plugin.cmd` 可访问、专用千牛浏览器可用，以及飞书机器人身份有效。通知项目不是上传 Plugin 的替代品。

### 5.2 首次部署由 Codex 完成

运维人员可以在 Codex 中新建一个本地项目任务，并发送以下部署要求：

请部署公司空坑位定时通知项目：

```Plain
https://github.com/kocotree/tmall-empty-slot-notifier.git
```

请完成以下工作：

1. 将 main 分支拉取或更新到当前本地项目目录，并安装项目依赖。
2. 检查 tmall-search-materials@tmall-materials-team Plugin 已安装且启用。
3. 通过 codex.cmd plugin list --json 获取当前 Plugin 的 installedPath，验证其中存在 scripts\run-plugin.cmd。
4. 根据 config.example.json 自动生成本机 config.local.json；不要让我手工填写 Plugin 安装路径、飞书 chat_id 或成员 open_id。
5. 验证飞书机器人身份、商品信息表、目标群和负责人映射。
6. 运行单元测试和 .\run-notifier.ps1 -DryRun，不要发送真实群消息。
7. 告诉我 dry-run 的巡检范围、负责人映射结果、待通知摘要和仍需人工处理的问题。

我没有把飞书 App Secret、Token、千牛 Cookie 或 NAS 凭据写入仓库、任务提示词或结果文件。

首次部署时，Codex 应自动完成 `git clone`/`git pull`、`uv sync`、本机配置生成和验证。业务用户不需要执行命令，也不需要复制 `config.example.json`。

`config.local.json` 仍然存在，是因为无人值守运行需要持久保存店铺、表格、群聊、负责人映射和本机入口等稳定配置；它是 Codex 生成和维护的本机运行文件，不是交给运营用户填写的安装参数。`config.local.json`、`state/`、`runs/` 和 `result.md` 已被 `.gitignore` 排除，禁止提交。

### 5.3 `plugin_root` 是内部运行值，不是用户配置项

通知程序当前需要通过 Plugin 的 `scripts\run-plugin.cmd` 调用公开采集命令，因此本机配置内部仍会保存 `plugin_root`。这个值只用于定位已经安装的 Plugin，不承载业务配置，也不应出现在面向普通用户的操作步骤中。

Codex 在部署和每次定时运行前应：

1. 执行 `codex.cmd plugin list --json`。
2. 精确查找 `tmall-search-materials@tmall-materials-team`，确认已安装且启用。
3. 使用返回的 `installedPath` 更新本机 `plugin_root`。
4. 验证 `<installedPath>\scripts\run-plugin.cmd` 存在后再启动巡检。

这样 Plugin 升级导致版本缓存目录变化时，不需要运维人员查找或修改“Plugin 实际安装路径”。开发目录路径只能作为本地开发、调试时的显式覆盖值，不能作为生产交付方案。

### 5.4 Codex 生成的本机配置

Codex 应根据 `config.example.json` 和当前电脑的实际环境生成配置，主要信息如下：

| 信息                       | 维护方式                                           |
| -------------------------- | -------------------------------------------------- |
| 千牛目标店铺               | 首次部署时由运维人员确认，Codex 写入               |
| Plugin 安装位置            | Codex 从 plugin list --json 自动解析并在运行前复核 |
| 商品 CSV、选择器和商品快照 | Codex 按项目约定路径生成或复用                     |
| 专用千牛浏览器地址         | 默认 http://127.0.0.1:9222，有变更时由 Codex 调整  |
| 商品信息表                 | 使用默认 Base 与 tblRr3NI24dvfwZ4                  |
| 目标群                     | 默认“打爆款小分队”                                 |
| 负责人名称映射             | 首次部署时由业务负责人确认，Codex 写入             |
| chat_id、成员 open_id      | 由 configure-lark.ps1 自动解析，不手工猜测或复制   |

### 5.5 绑定飞书机器人、群聊和负责人

飞书应用的 App ID 和 App Secret 只需由应用管理员在执行定时任务的 Windows 用户下配置一次。App Secret 不发送给普通运营人员，也不写入 Codex 定时任务提示词。

Codex 部署任务应验证：

lark-cli auth status --json --verify

.\configure-lark.ps1

配置脚本会精确搜索“打爆款小分队”、读取完整群成员列表，并把稳定的 `chat_id` 和负责人 @ 映射写入本机配置。群名不唯一、成员列表不完整或负责人无法唯一匹配时必须停止配置，交由运维人员核对，不能手工猜测 ID。

新增负责人、成员改名或群成员变化后，让 Codex 更新负责人名称映射并重新运行 `configure-lark.ps1`。

### 5.6 创建 Codex 定时任务

只有手工 dry-run 已经稳定通过后，才能创建定时任务。运维人员在同一个 Codex 本地项目中发送：

请为当前 tmall-empty-slot-notifier 本地项目创建一个 Codex 定时任务。

运行时间：按运营团队确认的北京时间和工作日频率执行。

每次运行时：

1. 检查当前启用的 tmall-search-materials@tmall-materials-team Plugin，并自动刷新本机配置中的安装路径。
2. 确认专用千牛浏览器可用且登录店铺正确。
3. 在当前项目目录运行 .\run-notifier.ps1。
4. 保留 state 和 runs，用于去重、重试和审计。
5. 只有程序判定需要通知时才发送“打爆款小分队”消息。
6. 如果登录失效、人机验证、店铺身份不符、飞书权限失效或采集结果不可信，不发送错误通知，并在任务结果中明确报告原因。

创建完成后，运维人员应检查 Codex 的定时任务页面，确认项目目录、运行时间、任务状态和最近一次结果。电脑必须保持开机，Codex 桌面应用必须保持运行，本地项目和专用浏览器必须可用。

通知程序的正式运行规则保持不变：

- 每次先完整分页更新商品信息快照；刷新失败时保留上次成功快照。
- 汇总为 0 时不发消息，但更新观察状态。
- 非零结果与上次完全相同时不重复通知。
- 负责人总数、等级分布或未分配商品集合变化时才发送新消息。
- 发送失败不会把本次结果标记为已经成功通知，下次仍可重试。
- 同一时间只允许一个实例运行；运行锁会阻止重复启动。

运维人员应定期查看 Codex 定时任务的最近运行结果，以及通知项目的 `runs/`、`result.md` 和 `state/notification-state.json`。

## 6. 数据、缓存与清理

### 上传 Plugin

- 用户级运行环境：`%LOCALAPPDATA%\tmall-search-materials\runtime`
- 任务数据：默认位于 `%LOCALAPPDATA%\tmall-search-materials\runs`
- 飞书本机快照：运行环境下的 `lark` 子目录
- Codex Plugin 缓存：`%USERPROFILE%\.codex\plugins\cache\tmall-materials-team\tmall-search-materials`

任务目录包含状态、日志、预览、裁剪结果和审计证据，长期使用会占用 C 盘。只能清理已经结束且无需审计恢复的旧任务，不得在任务运行中删除当前 session。

### 通知项目

- `runs/`：每次巡检的 CSV、checkpoint 和完整度矩阵。
- `state/product-metadata-snapshot.json`：上次完整成功的商品信息快照。
- `state/notification-state.json`：上次观察和成功发送签名。
- `result.md`：最近一次需要通知的本地文本结果。

清理通知状态会让系统把下一次非零结果视为首次结果并再次发送；执行前必须确认业务影响。

## 7. 常见故障与恢复

| 现象             | 优先检查                                                     | 恢复原则                                                     |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 安装后仍是旧版本 | 安装提示词中是不是使用了原先的gitee地址                      | 使用当前维护的github地址                                     |
| 千牛触发风控     | 目前已经解决了抓取空坑位的风控，但是后面抓取描述词和标题的风控可能还是会触发 | 用户侧可能需要在使用的过程中滑动解锁一下风控触发的滑动解锁。 |
| C 盘持续增大     | Plugin runs、预览/裁剪输出、安装缓存和通知 runs              | 仅清理已结束的旧任务与废弃版本缓存，并保留所需审计资料       |

## 8. 安全与权限边界

以下内容没有进入两个 GitHub 仓库：

- 飞书 App Secret、access token、refresh token、授权 device code。
- 千牛 Cookie、浏览器用户数据、账号和密码。
- NAS 账号、密码或 Windows 凭据。
- `config.local.json`、本机绝对安装缓存路径、运行状态和真实业务导出数据。
- 未脱敏的商品、成员、聊天 ID 或上传审计文件等。

NAS 读取默认只读。

## 10. 维护建议

- 上传 Plugin 保持 `win` 为唯一 Windows 生产分支；如果用户侧出现问题时，可以修复问题之后，发布新版本，用户侧只需要更新新版本即可。
