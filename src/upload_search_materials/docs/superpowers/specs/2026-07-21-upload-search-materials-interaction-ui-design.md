# upload-search-materials 交互式任务页面设计规格

## 1. 目标

为 `upload-search-materials` 增加一个可复用的本地交互页面，让用户能够在需要人工判断的阶段查看 Agent 产物、补充信息、确认选择，并把结构化 JSON 交还给 Agent 继续执行。

每次完整执行创建独立的时间戳任务目录，保存输入、交接、结果、事件和证据，使任务可恢复、可审计，并避免不同批次相互污染。

本页面是交互与审查层，不直接执行天猫上传、发布或浏览器生产操作。生产动作仍由 Agent 调用已有 CLI，并受现有审批与安全门禁约束。

## 2. MVP 范围与非目标

### 2.1 本次范围

- 本地 Flask 服务，仅监听 `127.0.0.1`。
- Jinja2 页面与原生 JavaScript，不引入前端构建链。
- 左侧阶段导航、中央工作区、底部固定交接栏。
- 10 个阶段的统一状态、表单、结果和恢复体验。
- 页面输入保存为 JSON，Agent 输出以独立 JSON 返回。
- 当前 Agent 通过文件等待机制接收用户提交。
- Codex 任务结束后，通过页面生成的恢复指令继续。
- 每次任务使用时间戳目录隔离，可显式恢复已有任务。
- 页面组件和阶段定义采用配置驱动，后续阶段不从零设计。

### 2.2 非目标

- 页面不保存账号、密码、验证码、Cookie 或浏览器凭证。
- 页面不直接调用天猫后台，不直接点击上传或发布。
- 页面不绕过 Codex 的任务生命周期自动唤醒已结束的 Agent。
- 本轮暂不测试视频素材；视频字段保留但显示为“已延期”。
- 本轮不建设多用户、远程部署、数据库服务或权限中心。

## 3. 方案选择

采用“JSON 文件交接 + 当前 Agent 等待”方案。

与网页直接执行 CLI 相比，该方案保持页面和执行器的职责分离；与网页直接调用 Codex 回调相比，不依赖当前不存在或不稳定的任务唤醒接口。

## 4. 总体架构

```text
Browser UI
  -> Flask interaction server
      -> input.json       用户输入
      -> handoff.json     提交信号与输入摘要

Active Agent
  -> wait-handoff        等待 handoff.json
  -> verify              校验任务、阶段、版本和 SHA-256
  -> existing CLI        执行扫描、匹配、dry-run 或生产命令
  -> result.json         结果、阻塞项、证据与下一步

Browser UI
  <- polling/result API  读取结果并刷新阶段状态
```

Flask 服务负责表单校验、原子写入、只读结果展示和目录边界保护。业务规则、素材判断、dry-run、审批清单和生产执行仍属于 Agent 与现有 Python 包。

## 5. 任务目录与隔离

默认任务根目录为项目内的 `runs`，可以通过 `TMALL_RUNS_ROOT` 指向其他明确目录。

```text
runs/
  20260721_143025/
    session.json
    events.ndjson
    01-setup/
      input.json
      handoff.json
      result.json
      evidence/
    02-completeness/
    03-scope/
    04-asset-matching/
    05-image-review/
    06-slots-copy/
    07-dry-run/
      output/
        run.json
    08-approval/
    09-production-confirmation/
    10-results/
```

- 新任务 ID 使用本地时间 `YYYYMMDD_HHMMSS`。
- 同一秒发生冲突时追加 `_02`、`_03`。
- 首页提供“新建任务”和“恢复已有任务”，不会静默复用最近任务。
- 服务只能访问配置任务根目录内的规范化路径，拒绝 `..`、符号链接越界和任意绝对路径拼接。
- 原始素材保持只读；裁剪等派生文件只写入当前任务的 evidence/output 目录。

## 6. 会话与交接协议

### 6.1 `session.json`

保存：

- `schema_version`
- `session_id`
- `created_at`、`updated_at`
- `current_stage`
- 各阶段状态与 revision
- `runs_root`
- `video_test_deferred`
- 最近一次 Agent 心跳时间

阶段状态统一为：

```text
draft
ready_for_agent
processing
needs_user_input
completed
blocked
```

### 6.2 `input.json`

页面拥有该文件的写权限。至少包含：

- `schema_version`
- `session_id`
- `stage_id`
- `revision`
- `submitted_at`
- `values`
- `user_notes`

### 6.3 `handoff.json`

页面在 `input.json` 成功落盘后才写入：

- `schema_version`
- `session_id`
- `stage_id`
- `revision`
- `status: ready_for_agent`
- `input_sha256`
- `created_at`

### 6.4 `result.json`

Agent 拥有该文件的写权限。至少包含：

- `schema_version`
- `session_id`
- `stage_id`
- `revision`
- `input_sha256`
- `status`
- `summary`
- `items` 或结果文件引用
- `blocking_reasons`
- `evidence`
- `next_action`
- `completed_at`

页面只接受 session、stage、revision 和输入哈希全部相符的结果。旧 revision 的结果显示为历史记录，不覆盖当前状态。

### 6.5 原子写入与修改失效

- JSON 先写临时文件，刷新并关闭后通过同目录重命名替换目标。
- 用户修改已提交内容时 revision 加一。
- 修改会使当前阶段原审批和所有依赖该输入的后续审批失效。
- `events.ndjson` 追加记录创建、提交、接收、完成、阻塞、修改和恢复事件，不写敏感信息。

## 7. Agent 继续执行机制

### 7.1 Agent 在线时

1. Agent 创建或恢复任务目录。
2. Agent 启动本地页面，并运行阶段等待命令。
3. 用户填写页面并点击“提交给 Agent”。
4. 页面校验必填项，写入 `input.json` 和 `handoff.json`。
5. 等待命令检测到交接文件后退出。
6. Agent 校验 `input_sha256`，把阶段改为 `processing` 并继续调用业务 CLI。
7. Agent 写入 `result.json`；页面轮询读取并更新状态。

页面按钮文案与状态必须准确：

- 编辑时：`保存草稿`、`提交给 Agent`
- 已提交：`已提交，等待 Agent`
- Agent 接收后：`Agent 处理中`
- 需要补充：`补充后重新提交`

### 7.2 Agent 不在线时

网页不能宣称已启动 Agent。若超过心跳阈值仍未接收，显示“Agent 未连接”，同时提供：

- `复制恢复指令`
- 当前任务目录
- 当前阶段
- 最近一次提交时间

恢复指令格式：

```text
继续执行 upload-search-materials。
任务目录：<absolute-session-path>
从 <stage_id> 阶段读取 handoff.json，校验 input_sha256 后继续。
```

用户回到原 Codex 任务粘贴该指令后，Agent 通过现有恢复入口继续。未来若产品提供正式任务唤醒 API，可新增适配器，不改变页面的数据协议。

## 8. 页面布局与可复用组件

采用用户已选择的 A 布局：左侧阶段导航。

```text
+----------------+-----------------------------------------+
| 任务与阶段导航 | 阶段标题 / 状态 / 任务 ID / revision    |
|                |-----------------------------------------|
| 01 任务配置    | 摘要卡、筛选、表格/画廊、输入表单       |
| 02 完整度巡检  |                                         |
| ...            |                                         |
| 10 结果与恢复  |-----------------------------------------|
|                | 保存草稿 / 提交给 Agent / 连接状态      |
+----------------+-----------------------------------------+
```

可复用组件：

- `AppShell`：整体布局、任务信息和导航。
- `StageRail`：阶段状态、阻塞数量、完成度。
- `StatusBadge`：统一状态文案与颜色。
- `SchemaForm`：根据字段配置生成输入框、选择器、复选框和路径输入。
- `InspectionMatrix`：基础素材与搜推素材完整度矩阵。
- `ProductScopeTable`：维护/排除决策与原因。
- `AssetMatchGallery`：图片缩略图、来源、授权、匹配依据和选择。
- `CropDecision`：原比例、目标比例与处理决定。
- `SlotBoard`：3/9 坑位编排与素材分组。
- `CopyEditor`：标题和描述编辑、规则校验。
- `DryRunSummary`：任务、阻塞、警告和证据汇总。
- `ApprovalChecklist`：精确 task ID 审批。
- `ProductionConfirmation`：店铺、商品、坑位、数量和哈希确认。
- `ResultTimeline`：发布、回查、异常与恢复记录。
- `HandoffBar`：草稿、提交、等待、连接状态和恢复指令。

阶段由配置声明标题、说明、输入字段、结果组件、前置条件和是否只读。新增阶段优先增加配置和专用结果组件，不复制完整页面。

## 9. 十个交互阶段

### 01 任务配置

显示：任务 ID、创建时间、运行模式、当前项目根目录。

输入：目标店铺、目标月份、商品范围、商品表、规则表、基础素材表、搜推素材表、图片素材根目录/清单、运行目录。路径提供选择/粘贴接口和可读性检查，不接收凭证。

### 02 完整度巡检

显示两部分：

- 基础素材矩阵：主图、视频、白底图、透明图、场景图、Logo 等后台字段的已上传/缺失/未知状态。
- 搜推素材矩阵：目标坑位数、现有图文数、现有视频数、空坑位、后台补采状态。

输入：用户可确认巡检结果、标记误判、填写覆盖原因。筛选包括全部、待补充、需后台补采、完整、排除候选、异常。

### 03 维护范围确认

显示：每个商品命中的月度规则、产品等级及 UVNO、清仓、好物体验、会员日、积分等排除理由。

输入：每个商品选择“本次维护”或“排除”，覆盖自动判断时必须填写原因。所有输入商品都保留唯一审计结果。

### 04 素材匹配

显示：候选图片、来源路径、来源系统、商品 ID/SKU/名称匹配方式、授权状态、尺寸、哈希、异常原因。

匹配标签严格区分：

- `商品 ID 命中`
- `SKU 命中`
- `已确认别名`
- `名称候选 · 待确认`

“别名命中”只用于用户已确认并保存的显式别名映射；模糊名称推断不得标记为已确认。

输入：图片源路径、来源类型、显式别名、逐文件或分组授权状态、采用/排除选择和备注。视频入口保留但禁用，标记“本轮测试延期”。

### 05 图片适用性与裁剪

显示：格式、宽高、比例、组内比例一致性、重复指纹、授权状态和规则原因码；原图与裁剪预览并排显示。

输入：图片策略、容差、直接使用/生成裁剪副本/人工处理决定。页面只记录决定；实际处理由 Agent 执行，且不得覆盖原图。

### 06 坑位编排与文案

显示：商品的 3/9 坑位目标、现有与待补坑位、图文/视频构成、素材组、标题和描述规则校验。

输入：坑位素材分配、素材组顺序、标题、描述和人工备注。本轮无视频时优先安排图文，不虚构视频素材。

### 07 全量 dry-run 审查

显示：商品总数、维护/排除/阻塞数量、任务数量、缺口、警告、素材与文案摘要、输入哈希及证据链接。

输入：返回修改、确认 dry-run 结果、对非阻塞警告的处理说明。dry-run 不生成生产发布结果。

### 08 精确任务授权

显示：仅列出 `ready_for_review` 的 task ID、商品 ID、目标坑位、媒体哈希、标题、描述和授权状态。

输入：精确选择 task ID、批准人、批准时间、有效期和确认勾选。生成的批准清单绑定内容哈希；内容变化立即失效。

### 09 生产确认

显示：目标店铺、商品 ID、坑位、最大商品数、精确 task ID、批准清单哈希、浏览器连接/选择器检查结果。

输入：最终确认勾选和备注。页面只生成生产确认交接，不能自行执行发布。1–3 商品试运行仍需用户在当前对话中明确授权。

### 10 结果与恢复

显示：各任务提交次数、远端素材 ID、审核状态、回查证据、失败/不确定原因和最后安全检查点。

输入：仅在异常时提供恢复请求、人工处理说明和“确认远端不存在后允许重试”的受控选择。`publish_uncertain` 默认禁止直接重试。

## 10. 信息完整性规则

每个阶段顶部固定显示：任务 ID、目标店铺、目标月份、阶段状态、revision、最近保存时间和 Agent 连接状态。

页面不得只显示汇总数字而隐藏判断依据。商品决策必须能展开查看来源字段、匹配方式、原因码和证据路径。

示例数据必须标记“示例”，不得把占位数字展示为真实扫描结果。例如未经真实统计时，不显示“分龄成长太阳镜 · 18 张”；应显示“名称候选 · 待确认”及实际扫描数量或“尚未扫描”。

## 11. 校验、错误与安全处理

- 前端校验用于即时提示，服务端必须重复校验。
- 必填项缺失、路径不可读、枚举无效或 revision 冲突时不生成 handoff。
- JSON 格式错误、哈希不一致和旧 revision 结果显示为阻塞，不静默忽略。
- Agent 处理超时只显示“尚未接收/处理中”，不推断成功或失败。
- 页面不提供生产发布快捷按钮。
- 店铺不一致、验证码、登录失效、选择器失效、内容哈希变化和发布结果不确定时继续沿用现有安全停止规则。

## 12. 测试设计

### 12.1 交互服务自动化测试

- 时间戳任务目录创建、冲突后缀和显式恢复。
- 目录穿越、越界路径和非法 session ID 被拒绝。
- 10 个阶段配置可加载，必填输入接口存在。
- `input.json`、`handoff.json` 原子写入及 SHA-256 正确。
- revision 增加会使旧结果和下游批准失效。
- Agent 结果的 session/stage/revision/hash 校验。
- 未连接、等待、处理中、需补充、完成和阻塞状态转换。
- 恢复指令包含绝对任务目录和精确阶段。

### 12.2 页面验收

- 左侧 10 阶段在常见桌面尺寸下完整可达。
- 每个阶段要求显示的信息均有真实数据位置或明确的空状态。
- 每个需要用户判断的字段均有输入控件、校验提示和保存状态。
- 完整度矩阵能区分基础素材与搜推素材。
- 别名状态不会把模糊匹配误显示为“已确认别名”。
- 提交后按钮状态准确，Agent 不在线时能复制恢复指令。
- 页面刷新和服务重启后能恢复草稿、提交状态和 Agent 结果。

### 12.3 Agent/Skill 测试

修改 `SKILL.md` 前先运行不加载新交互说明的基线场景，记录 Agent 是否：

- 跳过页面输入直接猜测用户选择；
- 把已提交误当成已执行；
- 在任务结束后宣称网页能自动唤醒 Agent；
- 读取旧 revision 或未校验哈希；
- 绕过生产审批。

更新 Skill 后使用相同场景复测，要求 Agent 正确创建任务、等待交接、校验输入、写入结果、安全恢复并保持生产门禁。

### 12.4 端到端测试顺序

在现有测试主线中增加“交互页面与任务隔离”阶段，并按以下顺序执行：

1. 测试环境。
2. 交互页面与任务隔离。
3. 素材清单/图片入口；视频延期。
4. 图片策略。
5. 生产选择器只读验证。
6. 全量 dry-run。
7. 1–3 商品生产验收。
8. 更新文档和发布状态。

生产验收仍必须单独获得用户明确授权，不因页面测试通过而自动开始。

## 13. 验收标准

- 每次新任务都有独立时间戳目录，任务可恢复且不会自动串批次。
- 页面完整覆盖 10 个阶段所需展示信息和用户输入接口。
- 用户提交后，在线 Agent 能通过 handoff 继续；离线时页面明确提示并生成可用恢复指令。
- 页面、Agent 和 CLI 文件职责分离，revision 与哈希防止读取过期输入。
- 页面不直接执行生产上传或发布。
- 页面布局和组件可通过阶段配置复用于后续流程。
- 自动化测试、页面人工验收、Skill 压力场景和更新后的 `test_plan.md` 均通过后，才标记交互功能完成。
