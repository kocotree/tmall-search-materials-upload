# Plugin 发布与测试流程

本文档定义本项目 Plugin 从开发完成到测试端验收的专项流程。触发条件和加载要求由仓库根目录 `AGENTS.md` 的“Plugin 发布与测试流程”章节规定。

1. 开发阶段先完成代码、Skill、参考文档和测试修改，再运行针对性测试、受影响模块回归、语法检查、`git diff --check` 与 Skill/Plugin 结构校验。版本号必须在这些工作完成后最后生成；版本号生成后如果又修改了任何会随 Plugin 分发的文件，必须重新生成一个从未发布过的新版本号。
2. Plugin 版本是不可变发布标识。同一个版本号只能对应唯一且固定的一套文件内容，禁止在 Gitee、Marketplace 或本机安装缓存中以“相同版本号、不同代码内容”的方式覆盖发布。任何会影响安装内容或运行行为的变更，包括 `src/`、`skills/`、`scripts/`、`config/`、`references/`、manifest 和启动契约，都必须发布新版本。
3. 发布前核对 `.codex-plugin/plugin.json` 中的版本号、当前 Git commit、待提交文件和 diff 范围；提交并推送后，再确认远程 `main` 指向预期 commit，远程 manifest 的版本号与本次发布一致。不得先让测试端安装某个版本，再继续修改该版本的内容。
4. 必须区分以下三个更新层级，不能把其中任意一层更新成功等同于整套运行环境已更新：
   - `codex plugin marketplace upgrade tmall-materials-team` 只更新 Marketplace 清单及其 Git 检出。
   - Plugin 安装会根据 manifest 版本写入或复用本机版本缓存；如果版本号未变化，移除后重新添加仍可能复用旧缓存。
   - 已启动的工作台服务会继续使用启动时记录的 `project_root` / `workspace_root`，不会因为 Marketplace 或 Plugin 更新而自动热更新。
5. 测试端更新时，应先升级 Marketplace，再安装带有全新版本号的 Plugin，并使用 `codex plugin list` 核对 installed、enabled、版本号和来源。仅看到版本号正确还不够；必须抽查安装缓存中的关键修复文件，必要时比较仓库、Marketplace 检出和安装缓存的文件哈希或目标代码片段，确认安装内容与远程 commit 一致。
6. Plugin 更新后必须用新版本的启动入口重启工作台。恢复既有任务时，应显式复用原 `runs` 根目录和 `session_id`，但让服务的 `project_root` / `workspace_root` 指向新 Plugin 目录；不得用可能保留旧项目根目录的通用重启方式冒充升级成功。重启不会要求重新采集已持久化的前序数据，但必须先核对会话状态和阶段。
7. 前端问题测试前，应核对工作台状态文件中的版本路径、端口、URL 和会话 ID，并只在用户手工验收时给出精确的当前工作台 URL。若浏览器报错，应同时检查服务实际返回的静态资源，而不能只看仓库文件；若后端日志没有对应请求，优先判断为前端脚本在发请求前失败。必要时比较静态资源哈希，以区分浏览器缓存、旧工作台进程和旧 Plugin 安装缓存。
8. 正式交给用户进行交互测试前，Codex 应完成以下只读验收：远程 commit 与版本一致、安装缓存包含修复、工作台由新 Plugin 根目录启动、页面返回新静态资源、目标会话仍指向原业务数据。任一项不满足，都不得让用户重复点击或重新执行业务流程来碰运气。
9. 如果发现“同版本号已安装过，但之后又修改了代码”，不得要求用户反复执行相同的 Marketplace 更新或移除/添加命令。正确处理方式是停止该版本的测试，生成新版本、重新发布和安装，再从新 Plugin 根目录恢复原会话。交付说明中应明确这是发布缓存问题，而不是用户更新操作错误。
